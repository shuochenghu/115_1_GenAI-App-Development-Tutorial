# 第 13 週教材規劃｜Function Calling 與 Skill-like 模組設計

- 課程：生成式 AI 應用開發
- 課堂核心：150 分鐘
- 實作案例：把有標籤的會議筆記整理成可核對的決議與待辦，再讓模型決定是否使用這項能力。
- 本檔是教案與製作規格。Notebook、App 和測試素材列於後續交付清單。

## 1. 課程銜接與學習成果

承接第 2 週的函式、dict／list 與 JSON，第 3 週的 Responses API，第 6 週的 Schema，以及第 7 週的表單觸發。第 11 週的證據核對和第 12 週的未知欄位處理沿用於會議筆記。本週由應用程式控制一次工具執行與結果回傳，第 14 週沿用工具契約，加入多步驟、重試與停止條件。第 15 週再討論 MCP 如何提供與連接工具。

下課前，學生能做到：

1. 用自己的話說明模型、Python 程式和工具各自負責的步驟。
2. 區分工具的輸入 Schema、Python 回傳的 JSON、模型產生的最後文字，指出三者各自需要的檢查。
3. 從呼叫項目讀出工具名稱、`arguments` 與 `call_id`，驗證參數後執行允許的函式，再以同一個 `call_id` 組裝回傳項目。
4. 從原始筆記查核至少一條決議或待辦，說明缺少期限、沒有工具呼叫、工具輸入錯誤各應如何呈現。

## 2. 實作方法與取捨

| 方法 | 執行責任與驗證方式 | 課堂安排 |
| --- | --- | --- |
| Python 直接呼叫 | 程式依固定規則處理筆記。零模型請求，可對照預期 JSON 測試模組。 | 必做前導。同一支函式也是模型可選的工具。 |
| Structured Outputs | 模型依輸出 Schema 抽取欄位。通常一次請求，適合自由逐字稿。須檢查拒答、未完成及原文證據。 | 教師用第 6 週例子對照。比較「限制答案格式」和「限制工具參數」，學生無須再做一套。 |
| Responses API 自訂 Function Calling | 模型選擇是否呼叫並提出參數。程式負責驗證、執行與回傳。典型工具成功路徑兩次請求，途中資料可逐步檢查。 | 本週主線。單一唯讀工具，先手動跑通，再接 API。 |
| 平台內建工具／Agents SDK | 平台執行內建工具，或由框架協助管理迴圈與追蹤。功能、資料與成本取決於工具和部署方式。 | 認識即可。第 14 週先看懂迴圈，第 15 週再比較 MCP。 |

官方查核： [Function calling](https://developers.openai.com/api/docs/guides/function-calling)、[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[Using tools](https://developers.openai.com/api/docs/guides/tools)。

## 3. 會議紀錄模組契約

`process_meeting_notes(notes: str) -> dict` 採本機可重現的文字規則。第一版使用虛構的課程活動籌備筆記，核心輸入為有標籤的短筆記。自由逐字稿的語意抽取留作延伸。模組的任務說明、輸入規格、可預期輸出、錯誤行為與測試資料共同構成這週的 Skill-like 模組。

- 輸入為去除首尾空白後 1～4,000 字元的文字。每行採 `重點：內容`、`決議：內容` 或 `待辦：事項｜負責人｜期限`。待辦的負責人與期限欄可留空，事項必填。待辦欄位分隔格式錯誤或標籤後內容為空時，回報行號及修正方式。
- 輸出為 `key_points`、`decisions`、`action_items`。重點／決議每筆含 `text` 和 `source_line`，待辦每筆含 `task`、`owner`、`due` 和 `source_line`。行號由 1 起算，依原始筆記計算。未知欄位用 JSON `null`，無相應項目用空清單。
- 忽略空行及未標籤的背景行。完全無可辨識標籤時顯示「沒有可整理的標籤」，帶學生檢查輸入格式。原文、模型參數與工具回傳都當資料處理，僅執行寫明的白名單函式。
- 正常例含重點、場地決議及一筆有負責人和期限的待辦。資訊不足例保留待辦事項及空白負責人／期限。兩筆皆使用人工預期 JSON，核對輸出值和原文行號。

## 4. 教學流程與程式分工

| 時間 | 活動 | 完成證據 |
| ---: | --- | --- |
| 15 分 | 方法比較。用同一份筆記看直接呼叫、結構化回答與模型工具呼叫。 | 能指出每種方法由誰處理筆記。 |
| 25 分 | 完整離線示範。直接執行本機函式，查看 JSON、空欄與原文行號。 | 能解釋 `null` 與空清單的差別。 |
| 20 分 | 教師示範手寫呼叫項目。依序辨識名稱、解析參數、執行、配對 `call_id`。 | 能從輸出追查到原本是哪一筆工具呼叫。 |
| 35 分 | 必做 A。完成工具輸入 Schema 和結果配對，跑固定測試。 | 正常案例回傳 JSON，錯誤案例保留錯誤狀態。 |
| 30 分 | 真實 API 教師示範與必做 B 判讀。比較「整理筆記」與「解釋何謂決議」。 | 能從 `response.output` 判讀有無工具呼叫並核對內容。 |
| 25 分 | 表單 App 展示、除錯、繳交與第 14 週銜接。 | 找出一個錯誤原因並記錄修正或預期。 |
| **150 分** | **課堂核心** | **先完成離線 A，再做 B 的追蹤與證據核對。** |

**A 的學生責任**為填寫工具的 `parameters` 和結果配對函式。Schema 保存於 `meeting_tool`，只接受必要的字串欄位 `notes`，開啟 strict 並禁止額外欄位。結果配對函式接收呼叫的 `call_id: str` 和已驗證的 `result: dict`，回傳可追加至下一次請求的 dict 並保存為 `tool_output`。先執行完整示範，再重跑修改過的定義格和固定測試格。Python 筆記處理、允許清單、參數驗證和測試器由教材提供，教師版補上 A 的答案與預期結果。

**B 的學生責任**為標記每筆案例中模型提出的行為、工具是否實際執行、原始輸出與最後回答的差異。沒有 API 可使用明確標示為手寫的教學案例，真實模型欄填「未測」。沒有呼叫且直接回應是可觀察結果。如果整理任務沒有呼叫，記為工具未執行。

### 真實 API 示範規格

1. 第一輪提交已驗證的筆記及任務，使用 Responses API 的自訂函式、`tool_choice="auto"` 和 `parallel_tool_calls=False`。用 `response.output` 取出呼叫項目。無工具呼叫時依狀態顯示直接文字或失敗訊息。
2. 先檢查回應狀態、呼叫數與工具名，再解析 `arguments` JSON。檢查欄位及型別，確認傳入筆記與提交原文一致，才執行一次本機函式。預期錯誤顯示原因並結束這次操作。用手寫測例檢查未知工具、壞 JSON、超限與重寫筆記等分支。
3. 第二輪沿用原始輸入及第一輪完整輸出項目，保留推理項目（如有），並附加 `function_call_output`。用呼叫項目的 `call_id` 配對，`output` 放序列化的工具結果。第二輪設定 `tool_choice="none"` 收尾，讓模型依結果撰寫摘要。最後檢查拒答、未完成或空文字。工具結果單獨呈現，成功摘要才標為完成。
4. Notebook 真實 API 開關放在活動格，預設關閉。整理成功路徑兩次請求，直接回答路徑一次。教師示範兩題預計共三次，以實際路徑記錄。每筆提交最多兩次請求，課堂預設關閉自動重試。以課程模型設定為起點，實作時用教學帳號確認可用性。示範全程使用虛構資料。

## 5. 後續教材交付與驗收

| 交付物 | 製作範圍 |
| --- | --- |
| Colab Notebook 學生／教師雙版及同名 Markdown | 同章節、固定格代號、依賴順序和測試。學生保留 A 的兩個相鄰 TODO，教師有完整答案、預期結果及誤解提示。完整示範不依賴學生 TODO。 |
| 單頁 Streamlit 配套 | 貼上筆記、選擇離線或模型工具呼叫、以表單提交，展示工具事件、JSON、摘要或錯誤。預設離線，新提交清除舊結果，rerun 與下載不發請求。App 採相同模組規格和判讀方式。 |
| 教師導讀、樣本與驗收 | 提供兩份虛構筆記、人工預期 JSON、手寫正常／無呼叫／錯誤事件，以及真實 API 示範的操作和記錄欄位。 |

**課堂完成條件**為 A 的固定測試通過，B 能交一筆正常整理、一筆資訊不足的原文核對，以及一條無工具呼叫或錯誤路徑的觀察。課後可換一份虛構筆記重跑並附修正紀錄。建議評量為工具契約與配對 40%、資料與原文核對 30%、錯誤分流 20%、可重現紀錄 10%。

**製作驗收**分開記錄 Notebook 結構、跨格依賴、雙版差異與離線固定測試，另列 Colab、真實 API 及 App 啟動與操作測試。固定資料至少覆蓋正常、資訊不足、無工具呼叫、未知工具、參數無效、`call_id` 不符、拒答／未完成與新提交狀態清除。本次交付為教材規劃，這些實作測試待教材製作後執行。
