# 第12週實作方法比較與建議

2026-11-03查核；正式主線維持OpenAI Responses與課程gpt-5.4-mini。選擇以本週「看懂圖片輸入、未知值與原圖查核」為目標，不按工具數量增加作業。

## 先決定任務，再決定怎麼送圖片

單張圖片問答、收據抽取、整份PDF與大量文件檢索有不同責任。Base64、URL與file ID是同一模型的輸入方式；OCR與RAG則改變處理流程，不能把兩種比較混為一談。

| 方法 | 誰負責處理／可觀察證據 | 負擔與限制 | 本課建議 |
|---|---|---|---|
| Vision直接讀單圖 | 本機驗證並準備圖片；模型看圖，程式檢查回應，人回看原圖 | 小字、數字、位置與計數可能看錯；沒有檢索步驟 | 本週必做主線 |
| 本機OCR→文字／規則 | OCR先輸出文字，保留原圖與識別位置，再解析；可另交LLM | 多一個OCR環境與語言資料；錯字、表格與閱讀順序需查核 | 想掌握文字抽取或避免把原圖送外部服務時評估；本週不安裝 |
| 專用雲端OCR／文件解析 | 服務抽取文字、版面或欄位，程式保存對應證據 | 需另查服務格式、權限、資料政策與計價，不能假設一律比Vision準 | 大量固定文件時另做小規模評估；本週不新增另一平台 |
| PDF直接input_file | 支援Vision的模型可接收PDF文字與頁面影像 | 多頁輸入成本與單圖不同；需保留原頁並檢查頁面證據 | 整份小文件值得選；與第9週本機reader比較，選讀 |
| OCR／圖片描述→文字RAG | 自建或平台索引抽取文字，檢索後回連原圖／頁碼 | 上游辨識錯字會傳入索引；文字描述可能漏版面與物件 | 延伸第10～11週；先驗證抽取品質再建索引 |
| 影像檢索→Vision | 另選影像或多模態檢索模型，取候選圖片再問答 | 多一種索引、評估與成本；不能將本課文字Embedding當成圖片Embedding | 大量圖片需要找相似圖時再設計，非本週必做 |

OCR可只在本機執行，但後續把文字送LLM仍有外傳；不能以「有OCR」就保證隱私。[Tesseract官方說明](https://tesseract-ocr.github.io/tessdoc/)提供本機OCR與語言資料的入口，本次未安裝或實測。

PDF直接輸入與File Search是不同路徑：前者把本次文件交給模型，後者先建索引再檢索。File Search列出的支援格式不含PNG等單張圖片，不以直接上傳PNG當成本課可行路線；對PDF也不能只憑可上傳就聲稱圖表／掃描辨識品質已驗證。[官方File inputs](https://developers.openai.com/api/docs/guides/file-inputs)、[官方File Search](https://developers.openai.com/api/docs/guides/tools-file-search)

## 三種圖片傳輸的取捨

| 輸入方式 | 實際content欄位 | 前置與生命週期 | 請求與教學取捨 |
|---|---|---|---|
| Base64 data URL | input_image.image_url = data:image/png;base64,… | 已有圖片bytes；每次包含圖片，不建Files資源 | 每題1次Responses；字串約增1/3，主線最直接 |
| HTTPS URL | input_image.image_url = 可取用圖片網址 | 須可由服務取得、合法且穩定；不要依賴登入頁或會變動內容 | 每題1次Responses；省本機編碼，仍計圖片輸入成本 |
| Files API ID | input_image.file_id = 本次上傳圖片ID | 先以purpose="vision"上傳，保存ID並明確刪除；不是Vector Store ID | 先1次上傳，之後每題1次Responses，另1次刪除；重用ID不代表不計圖片token |

三種方式可用同一張圖片、問題、detail與輸出規格比較，不保證結果逐字相同。URL與file ID範本在雙版Notebook「選讀」格，**只建dict、預設0請求**；主線App只提供Base64，沒有隱藏的Files上傳或清理程序。[官方圖片輸入](https://developers.openai.com/api/docs/guides/images-vision)

若自行實作file ID：把收到的ID存進不提交的本機紀錄，再引用；操作失敗保留ID供清理，避免重複上傳。只對該紀錄ID呼叫`client.files.delete(file_id)`，不列舉刪除其他檔案。請求逾時未收到ID時，要在平台核對該次寫入；`store=False`與關閉App不會替你刪除原檔。[官方刪除介面](https://developers.openai.com/api/reference/resources/files/methods/delete)

## 文字問答與結構化抽取

| 做法 | 最適用途 | 限制 | 安排 |
|---|---|---|---|
| responses.create＋文字 | 描述、問題、截圖診斷 | 需人讀證據與推論，不能保證固定欄位 | 最小必看範例 |
| responses.create＋strict JSON Schema | UI須讀日期、總額與缺值 | 必須另外檢查拒答、完成、解析與語意；null不等於0 | 沿第6／8週完整提供，可作同App任務 |
| responses.parse＋Pydantic | 已選用第8週Pydantic者延伸 | 可減少手動結構驗證，但不會改善看圖品質；還需拒答／完成檢查 | 提供方向，非新增必做版本 |

兩種正式任務每次都只送一次Responses；不先問答再自動送抽取。換輸出格式是在比較程式讀取需求，不宣稱Schema讓模型更會看圖。[官方Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

## detail與模型選擇

本課沿用gpt-5.4-mini，官方列有圖片輸入與結構化輸出；帳號可用性仍需課前確認。主線預設auto，可另選high／low；官方現行列有original，密集大圖可評估，但本週採小圖且不需精確座標，故不加為必測選項。low並非固定較省，按實際usage及當時計價判斷。[模型頁](https://developers.openai.com/api/docs/models/gpt-5.4-mini)、[圖片成本估算](https://developers.openai.com/api/docs/guides/image-cost-calculator)

跨平台比較可延續課綱，但本週不新增Gemini／Claude或本機視覺模型安裝。若另選服務或本機模型，先核對圖片格式、部署需求、資料流與模型授權，再用同圖、同題與相同人工驗收評估；不得由某平台的支援情況推論另一平台。

## 為何這樣安排第9～13週

第9週先理解reader與資料品質；圖片或掃描件看不到文字時，需辨識而非再切塊。第10週理解檢索，第11週比較自行RAG與File Search，第12週補上圖片輸入與視覺證據。這些能力可組合，但本週不再加一個影像RAG專題。第13週再進入Function Calling與任務模組，先分清「模型理解輸入」和「程式執行動作」。

教師示範兩種輸出；學生作業選一種任務、沿用同一App，只做A與B。評量看輸入正確、原圖查核、未知與錯誤處理，不按上傳方式或模型新舊加分。若課前實測發現帳號、格式或辨識限制，先記錄並調整主線，不用手寫模型輸出補齊。
